# Архитектура API

## Статус и границы

Проект представляет собой модульный TypeScript API-каркас, построенный поверх Hono.

Архитектурный принцип: новый доменный функционал добавляется отдельными бизнес-модулями. Его нельзя прятать в `libs/core`, расширять через несвязанный демонстрационный модуль или смешивать с транспортным слоем.

## Карта слоёв

```text
apps/api-main
  main.ts                 точка входа процесса: сервер или миграции
  server.ts               корень композиции: Hono, промежуточные обработчики, контроллеры
  config/                 валидированная конфигурация из окружения
  database/               схема Drizzle для выполнения и миграции Knex
  datalayer/              репозитории и преобразование ошибок базы данных
  global/                 сквозные зависимости и промежуточные обработчики
  modules/                бизнес-модули и HTTP-контроллеры

libs
  core/
    kernel/               абстрактные контракты и базовые правила приложения
    runtime/              переиспользуемые технические реализации
  common/                 общие контракты, ресурсы и функции без состояния
  entities/               легковесные доменные сущности
  domain/<domain>/        переиспользуемая доменная логика и её типы
```

Правило размещения:

- `apps/api-main/modules/<module>` — сценарии использования и HTTP API конкретного домена.
- `apps/api-main/datalayer` — доступ через SQL/Drizzle; репозиторий не содержит HTTP-логику.
- `libs/entities` — доменные данные и небольшое локальное поведение.
- `libs/domain/<domain>` — общие бизнес-правила и расчёты, используемые несколькими прикладными модулями, вместе с необходимыми типами и константами.
- `libs/core` — только переиспользуемые инфраструктурные примитивы. Бизнес-логика конкретного домена сюда не помещается.
- `libs/common` — только действительно общие транспортные артефакты, а не контракты одного модуля.

## Core: kernel, runtime и common

### `libs/core/kernel`

`kernel` содержит только базовые абстракции приложения:

- интерфейсы, абстрактные классы, базовые типы и контракты протоколов;
- общие контракты жизненного цикла и репозиториев;
- правила взаимодействия слоёв.

`kernel` не содержит конкретные клиенты, ввод-вывод, HTTP-обработчики, Redis, WebSocket, доступ к базе данных, доменную логику или импорты из `apps/**` и `modules/**`.

### `libs/core/runtime`

`runtime` содержит переиспользуемые технические реализации, которые выполняют работу во время запуска приложения:

- примитивы HTTP-сервера, базовый контроллер, промежуточные обработчики, валидатор, обработку ошибок;
- клиенты Redis, базы данных, очередей и универсальные WebSocket-клиенты;
- утилиты жизненного цикла, повторные попытки, миграции и другие инфраструктурные адаптеры.

`runtime` может зависеть от `kernel`, внешних пакетов и других `libs/**`, но не от `apps/**` или доменных `modules/**`.

### `libs/common`

`common` содержит нейтральные контракты, ресурсы и вспомогательные функции без состояния, переиспользуемые несколькими модулями. Здесь допустимы общие контракты API, оболочки ответов, пагинация, чистые вспомогательные функции, преобразования, форматирование и примитивы валидации без ввода-вывода, жизненного цикла и доменных правил.

`common` не содержит инфраструктурные клиенты, доступ к HTTP/Redis/WebSocket/базе данных и бизнес-логику конкретного домена.

## Общая доменная логика: `libs/domain`

`libs/domain/<domain>/` содержит самостоятельные доменные операции, необходимые нескольким прикладным модулям. Общие бизнес-правила принадлежат доменной библиотеке, а сценарии и решения, специфичные для отдельного прикладного модуля, остаются в этом модуле.

Правила:
- переносить минимальную самостоятельную ответственность, а не весь прикладной модуль ради одной общей функции;
- хранить рядом с логикой необходимые типы, интерфейсы, константы и тесты; внутренние типы серверной части, включая входы и результаты публичных функций, размещать в локальном `types.ts`;
- переиспользовать существующие сущности из `libs/entities` без дублирования; доменные интерфейсы не переносить в `core/kernel` только потому, что это интерфейсы;
- оставлять HTTP-контроллеры, действия (actions), REST DTO, контракты, ресурсы и сценарии конкретного модуля в `apps`;
- передавать данные для операций аргументами; не создавать инфраструктурные клиенты, не читать окружение и не зависеть от HTTP-фреймворка;
- если доменной операции нужен ввод-вывод, объявить узкий интерфейс зависимости рядом с ней и передать реализацию при сборке приложения; не импортировать конкретные клиенты или репозитории в доменную библиотеку;
- предоставлять небольшой публичный API через `libs/domain/<domain>/index.ts`; потребители используют этот API, внутренние файлы — прямые локальные импорты, а не собственный файл реэкспортов;
- не создавать общий `libs/domain/index.ts`, экспортирующий все домены; дополнительные каталоги и абстракции добавлять только по реальной необходимости.

Общая схема структуры:

```text
libs/domain/<domain>/
  <operation>.ts
  types.ts
  index.ts
  __tests__/
    <operation>.test.ts
```

## Правило выбора расположения

- Базовая инфраструктурная абстракция или интерфейс без конкретного поведения во время выполнения → `libs/core/kernel`.
- Переиспользуемая техническая реализация с вводом-выводом, жизненным циклом или интеграцией с фреймворком → `libs/core/runtime`.
- Общий нейтральный контракт API, ресурс или чистая вспомогательная функция без состояния → `libs/common`.
- Общая доменная операция и её типы, необходимые нескольким модулям → `libs/domain/<domain>`.
- Сценарий, REST-контракт или логика, используемая только одним прикладным модулем → `apps/api-main/modules/<module>`.
- `libs/**` не импортирует `apps/**`, включая `import type`.

## Направление зависимостей

`apps` — верхний прикладной слой, `libs` — нижние переиспользуемые слои.

- `apps/**` может импортировать `libs/**`.
- `libs/**` не может импортировать ничего из `apps/**`.
- Запрет относится к импортам времени выполнения, `import type`, путям с псевдонимами, относительным путям и экспортам через файлы реэкспортов.
- `libs/**` может зависеть только от Node.js, внешних пакетов и других модулей в `libs/**`.
- Если коду внутри `libs/**` нужен тип или контракт, который сейчас объявлен в `apps/**`, этот тип или контракт нужно перенести либо выделить в `libs/**`. Импортировать его из `apps/**` нельзя.
- Код внутри `apps/api-main/modules/<module>/**` не импортирует другой прикладной модуль: запрет включает функции, классы, константы, типы, динамические импорты и реэкспорты, независимо от псевдонима или относительного пути. Публичный `index.ts` соседнего модуля не является исключением.
- Нельзя обходить запрет через промежуточный файл реэкспортов или реэкспорт в другом каталоге.
- `libs/domain` может использовать `libs/entities`, нейтральные вспомогательные функции из `libs/common`, базовые контракты `libs/core/kernel` и внешние пакеты без нарушения границы инфраструктуры. Эти нижележащие слои не импортируют `libs/domain`.
- Все зависимости между библиотеками должны быть ацикличными. Между доменными библиотеками допустимы явные однонаправленные зависимости; взаимная потребность требует пересмотра границ и выделения общей ответственности.

### Порядок выделения общей логики

1. Определить общую операцию и её ответственность: расчёт, бизнес-правило или тип. Не объединять код только из-за внешнего сходства.
2. Выделить минимальные входы, результаты и необходимые зависимости операции.
3. Перенести реализацию, связанные типы, константы и тесты в `libs/domain/<domain>/`, устранив зависимости от `apps`.
4. Обновить всех потребителей, включая исходный модуль, на публичный API библиотеки. При использовании нового псевдонима согласовать его с настройками компиляции, запуска и тестов.
5. Удалить прежние экспорты и копии реализации. Не оставлять реэкспорт для совместимости в прикладном модуле ради старого пути импорта.
6. Проверить сохранение поведения тестами, компиляцию и отсутствие запрещённых импортов и циклов. Автоматическая проверка архитектурных границ в CI должна учитывать псевдонимы, относительные пути и реэкспорты.

Сценарий, координирующий несколько модулей, собирается выше этих модулей через явные интерфейсы и переданные зависимости. Корень композиции может импортировать публичные точки сборки модулей; это не разрешает модулям импортировать друг друга.

### Владение инфраструктурными клиентами

Инфраструктурный клиент принадлежит слою, в котором он объявлен. Потребители импортируют клиент и связанные с ним контракты напрямую из слоя-владельца.

Нельзя создавать реэкспорт для совместимости, переименованный псевдоним или промежуточный модуль в другом слое только для сохранения прежнего пути импорта.

При переносе клиента в другой слой в том же изменении необходимо обновить импорты всех потребителей и удалить устаревшие промежуточные экспорты или каталоги.


## Корень композиции и регистрация модулей

`apps/api-main/main.ts` выбирает режим запуска: HTTP-сервер или миграции.

`apps/api-main/server.ts` является единственным корнем композиции. Здесь создаются приложение Hono, глобальные промежуточные обработчики, CORS, обработчики ошибок и контроллеры из `apps/api-main/modules/index.ts`.

Новый HTTP-модуль должен быть явно зарегистрирован в `modules/index.ts`. Автоматического обнаружения нет и оно не нужно: регистрация должна оставаться обозримой.

Каждый контроллер реализует `IBaseController`: предоставляет `routes` и асинхронный `init()`. Перед монтированием маршрутов `server.ts` вызывает `init()` каждого контроллера.

```text
Запрос
  -> Глобальные промежуточные обработчики Hono
  -> Маршрут контроллера
  -> Валидация DTO
  -> Action
  -> Сервис / Репозиторий
  -> Сущность / хранение
  -> Resource
  -> BaseController.execute
  -> JSON-ответ
```

## Модуль как единица бизнес-функциональности

Один модуль владеет одним доменным контекстом. Для нового доменного контекста структура должна быть такой:

```text
modules/example/
  actions/
  dependency/
  inout/
    validations/
    contracts/
    resources/
  services/
  example.controller.ts
  index.ts
```

Правила:

- контроллер связывает HTTP-маршрут со сценарием использования, но не реализует бизнес-логику;
- один `Action` выражает один сценарий использования;
- каждый класс `Action` хранится в отдельном файле `actions/<operation>-<entity>.action.ts`; `actions/index.ts` содержит только экспорты;
- `Action` не получает `Hono.Context` и не формирует HTTP-ответ;
- `Action` не создаёт сервисы через `new`; он использует только сервисы, созданные в `dependency.ts` и переданные через конструктор;
- сервис содержит переиспользуемые доменные операции, которые не принадлежат одному действию;
- чистые вспомогательные функции без состояния, зависимостей и жизненного цикла, используемые только этим модулем, размещаются в `modules/<module>/common/` в файлах с предметным именем, например `slugs.ts`, без суффикса `.service`; общая доменная логика нескольких модулей размещается в `libs/domain/<domain>/`;
- `services/` используется только для переиспользуемой доменной логики с самостоятельной ответственностью и реальными зависимостями;
- репозиторий скрывает Drizzle и детали запросов;
- ресурс преобразует внутренние данные в публичный контракт API;
- модуль не импортирует другой модуль, включая его публичный `index.ts`; общая логика и её типы принадлежат `libs/domain/<domain>/`.

Не нужно создавать модуль ради одной технической функции. Если код не имеет самостоятельной доменной ответственности, он остаётся рядом с владельцем сценария использования или в `libs/core` только при доказанной повторной применимости.

Новый модуль создаётся на основе `_templates/module`. Его внешний модульный интерфейс выражается через локальный `index.ts` для сборки приложения. Он не служит точкой переиспользования кода соседними модулями.

## Явные зависимости

Проект не использует глобальный контейнер внедрения зависимостей. Зависимости собираются вручную:

- глобальные зависимости — сквозные сервисы, например промежуточный обработчик JWT;
- зависимости модуля — репозитории и сервисы конкретного модуля; `dependency.ts` создаёт их один раз и передаёт через интерфейс зависимостей;
- действие получает репозитории и сервисы только через зависимости конструктора.

Это намеренный подход. Он делает связывание компонентов во время выполнения и владение зависимостями видимыми в коде.

Правила:

- не создавать локатор сервисов;
- в коде приложения читать `process.env` только в слое конфигурации; сервисы, действия, контроллеры, репозитории и доменные библиотеки не должны самостоятельно читать окружение;
- проверять значения в модулях конфигурации и передавать потребителям валидированную конфигурацию через явные зависимости;
- не превращать объект зависимостей в неявный глобальный контейнер;
- действия без состояния можно создавать на каждый запрос; объекты с состоянием требуют явно выбранного жизненного цикла.

## HTTP, DTO и публичные контракты

Входные данные проходят валидацию во время выполнения через DTO на базе Zod. DTO создаётся в контроллере до запуска действия.

```text
HTTP JSON -> DTO -> Вход действия
Сущность / доменный результат -> Resource -> Контракт -> API JSON
```

### Структура `inout`

Каждая сущность имеет собственные файлы контракта и ресурса: `contracts/<entity>.contract.ts` и `resources/<entity>.resource.ts`. Не объединять контракты или ресурсы разных сущностей в общий файл.

Каждый вход сценария использования имеет отдельный DTO-файл в `validations/` с именем `<operation>-<entity>.dto.ts`. DTO наследует `BaseValidator`, собирает итоговую Zod-схему и валидирует вход при создании.

`validations/schema.ts` содержит только переиспользуемые Zod-примитивы полей конкретного модуля. `index.ts` в `inout/` и его подпапках используется только для реэкспортов.

`contracts/` и `*.contract.ts` предназначены исключительно для типов публичного REST API — данных, которыми серверная часть обменивается с внешним потребителем. Они не должны быть типом строки Drizzle или сущности.

Типы и интерфейсы сервисов, действий, репозиториев и инфраструктурных клиентов размещаются в локальном `types.ts`.
Это относится также к параметрам и результатам их публичных методов.
Экспорт типа и использование другим серверным модулем не делают его контрактом REST API.
Например, `LockResult<T>` клиента Redis относится к `redis-lock/types.ts`.

`resources` — единственное обычное место для преобразования сущности в выходные данные API. Обычные бизнес-маршруты должны возвращать `Resource` или `ResourceList` через `BaseController.execute(...)`.

Стандартный ответ:

```json
{
  "status": 200,
  "data": {},
  "list": [],
  "pagination": {
    "limit": 20,
    "total": 0
  },
  "meta": {}
}
```

Для конкретного ответа используется либо `data`, либо `list`. Не нужно вручную собирать эту оболочку в контроллере.

Исключения: проверки работоспособности, перенаправления OAuth и другие чисто транспортные конечные точки могут возвращать ответ Hono непосредственно, если обработка через Resource для них не применима.

### Приоритет контракта серверной части при интеграции с UI

- Для интеграций клиентской и серверной частей контракт серверного API считается источником правды для UI.
- Не подгоняй структуру серверного ответа под текущие ожидания UI только ради удобства клиентской части.
- Серверная часть преобразует доменные данные в согласованный публичный контракт API через `Resource` или `ResourceList`. Это предусмотренное архитектурой преобразование; запрет относится к подгонке данных под конкретные UI-компоненты и их локальные модели отображения.
- Серверная часть не должна менять единицы времени, имена для отображения, сортировку, группировку, структуру данных для графиков или другие преобразования представления только потому, что так сейчас удобнее конкретному экрану.
- Если клиентская часть должна работать с новым или изменившимся серверным контрактом, адаптацию выполняй на стороне UI: в `src/api`, сервисе страницы, слое преобразований или ближайшей нормализации данных клиентской части.
- Если UI ожидает другой формат данных, именно UI должен преобразовывать серверный ответ под свои компоненты, графики, таблицы и локальные модели отображения.
- Серверная часть меняет контракт только тогда, когда это действительно доменное требование или требование уровня API, а не обходное решение под текущую реализацию UI.
- При расхождении между текущим UI и серверным контрактом исправляй UI так, чтобы он отражал фактические данные и ограничения серверной части, а не наоборот.

## Ошибки и авторизация

Ожидаемые ошибки выражаются через `AppError` и `ErrorCode`. Верхнеуровневый `globalExceptionHandler` конвертирует их в единый JSON-ответ с ошибкой.

Правила:

- ошибки валидации, бизнес-правил и репозиториев переводятся в `AppError`;
- не дублировать try/catch и HTTP-ответы с ошибками в каждом контроллере;
- неизвестные ошибки не должны утекать клиенту с техническими деталями;
- `JwtMiddleware` только извлекает идентичность из токена доступа;
- действие, которому требуется пользователь, получает `CurrentUserJwt` через `getCurrentUserJwt(c)`.

Авторизация должна быть частью сценария использования: получение идентичности в контроллере допустимо, но проверка владения и прав доступа принадлежит действию/сервису.

## Сущности и хранение данных

Сущности в `libs/entities` — легковесные классы. Они не являются ORM-моделями и могут содержать только локальное доменное поведение, например хеширование пароля или генерацию токена обновления.

Репозитории:

- выполняют запросы Drizzle;
- преобразуют строку базы данных в сущность;
- не отдают необработанные строки базы данных выше слоя данных;
- переводят специфичные для базы данных ошибки в `AppError`;
- не выполняют преобразования для представления.

Если несколько методов поиска одной сущности отличаются только дополнительными условиями одного поиска, репозиторий предоставляет один `findOneBy(filter)`. Тип `filter` должен быть узким доменным типом с обязательным ключом поиска; нельзя принимать `Partial<Entity>` или допускать пустой фильтр. Методы с разной бизнес-семантикой или разными правилами доступа не объединяются.

Для поиска, где отсутствие сущности является ошибкой сценария использования, репозиторий поддерживает опцию `{ findOrThrow: true }`. В этом режиме репозиторий выбрасывает `AppError(ErrorCode.NOT_FOUND)` и возвращает сущность, отличную от null. Не создавать сервис только для вызова репозитория и преобразования `null` в `NOT_FOUND`; сервис содержит только общую доменную логику модуля.

## Миграции базы данных

- Перед проектированием, созданием или изменением SQL-миграции обязательно прочитать [`migrations.md`](migrations.md).
- Документ задаёт обязательный стиль Knex, пример миграции и порядок проверки.
- Миграции писать через Knex Schema Builder по этому примеру. Не заменять доступные операции Knex ручными DDL-строками. Условия допустимого точечного SQL описаны в `migrations.md`.
- Изменение схемы данных всегда состоит из двух синхронных частей:
1. новая миграция Knex в `database/migrations`;
2. соответствующее изменение схемы Drizzle в `database/schemas`.

Миграция Knex описывает эволюцию реальной базы. Схема Drizzle описывает контракт времени выполнения. Ни одна из них не заменяет другую.

## Идентификаторы базы данных

- Для таблиц первичный ключ должен быть `bigint generated always as identity primary key`.
- Внешние ключи должны использовать тот же тип, что и связанный первичный ключ — обычно `bigint`.
- Не использовать `serial` и `bigserial` в новых схемах; применять `GENERATED ... AS IDENTITY`.

## Тестирование

- Основная точка тестирования — сервисы, реализующие бизнес-логику.
- Дополнительно тестируются вспомогательные и общие функции, если они содержат самостоятельные вычисления, преобразования или правила, влияющие на поведение бизнес-сценариев.

### Расположение

- Все тестовые файлы хранятся в `__tests__` внутри папки, которой принадлежит тестируемый код.
- Тест сервиса размещается в `services/__tests__/<name>.service.test.ts`.
- Тест вспомогательной функции размещается в `common/__tests__/<name>.test.ts` или в `__tests__` другой папки-владельца.
- Тестовые наборы данных, заглушки и вспомогательные функции хранятся внутри соответствующей `__tests__`.
- Рабочий код приложения не импортирует файлы из `__tests__`.

Пример:

```text
services/
  wallets.service.ts
  __tests__/
    wallets.service.test.ts

common/
  profit-drawdown.ts
  __tests__/
    profit-drawdown.test.ts
```

### Область тестирования

- Отдельные тесты контроллеров и репозиториев не создаются.
- Сервис тестируется через его публичные методы: входные данные, результат, бизнес-ошибки и значимые побочные эффекты.
- Если самостоятельная бизнес-логика находится в действии, она проверяется напрямую на уровне действия, без HTTP-контроллера.
  Создавать дополнительный сервис только ради тестирования не нужно.
- Простое делегирование, методы чтения свойств и тривиальные обёртки не требуют отдельных тестов без самостоятельного риска регрессии.

### Зависимости и изоляция

- В тестах сервисов репозитории и внешние зависимости ввода-вывода заменяются имитациями или заглушками через существующие точки передачи зависимостей.
- Проверяется решение сервиса: какие данные он возвращает, какие изменения запрашивает и какие операции запрещает.
  SQL, команды Redis и внутреннее устройство репозитория не проверяются.
- Чистые вспомогательные функции выполняются реально; их поведение не следует подменять, если оно является частью проверяемого сценария.
- Обычный запуск тестов не требует PostgreSQL, Redis, сетевых API или blockchain RPC.
- Время, таймеры и случайность контролируются там, где они влияют на результат. Тесты не зависят от порядка запуска.

### Содержание проверок

- Покрываются значимые бизнес-сценарии: успешное выполнение, нарушение правил, граничные значения, ошибки зависимостей и отсутствие запрещённых побочных эффектов.
- Проверки привязываются к наблюдаемому поведению, а не к закрытым методам или случайному порядку внутренних вызовов.
- Количество тестов и процент покрытия не заменяют проверки критичных бизнес-правил.

Для запуска используется Vitest: `npm test`.

## Критерии готовности нового модуля

Перед регистрацией модуля проверить:

- модуль имеет единственную понятную доменную ответственность;
- модуль не импортирует соседние модули; общая доменная логика выделена в `libs/domain`, зависимости библиотек не образуют циклов;
- маршрут зарегистрирован в `modules/index.ts`;
- входные данные валидируются DTO;
- действие не зависит от Hono;
- наружу возвращается контракт через ресурс;
- владение проверено в действии/сервисе;
- репозиторий не проникает в контроллер;
- миграция и схема Drizzle синхронизированы;
- конфигурация валидируется отдельным модулем конфигурации;
- критичные бизнес-сценарии покрыты тестами сервисов и, при необходимости, действий и вспомогательных функций; все тестовые файлы размещены в соответствующих `__tests__`.
