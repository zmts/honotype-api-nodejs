# Рекомендуемые практики JavaScript

## Назначение

Используй эти правила при генерации, изменении, рефакторинге и ревью JavaScript-кода.

Основная цель — корректный, читаемый, поддерживаемый код, соразмерный задаче.

При конфликте правил предпочитай:
1. корректность
2. ясность
3. явное намерение
4. меньшую сложность
5. согласованность с существующей кодовой базой

---

## 1. Общие правила

- Предпочитай читаемый код хитроумному.
- Предпочитай явный код сжатому.
- Предпочитай предсказуемое поведение эффектным приёмам.
- Сохраняй соразмерность изменений задаче.
- Следуй существующим соглашениям проекта, если они явно не вредят.

Не вводи сложность без конкретной пользы.

---

## 2. Языковые настройки по умолчанию

- Используй `const` по умолчанию.
- Используй `let` только при необходимости переприсваивания.
- Не используй `var`.
- Предпочитай `===` и `!==`.
- Предпочитай `async/await` сложным цепочкам промисов.
- Используй современный синтаксис только тогда, когда он улучшает ясность.

Не используй возможности языка только потому, что они доступны.

---

## 3. Правила обработки данных

- По умолчанию считай внешние данные недоверенными.
- Проверяй входные данные на границах.
- Нормализуй необработанные входные данные до их передачи глубже в бизнес-логику.
- Не предполагай, что объекты полны, корректно сформированы или безопасны.
- Избегай передачи необработанных внешних данных глубоко в систему.

Всегда проверяй данные из:
- HTTP-запросов
- очередей
- вебхуков
- переменных окружения
- JSON.parse
- localStorage/sessionStorage
- файлов
- внешних API
- сторонних SDK

Предпочтительный порядок обработки на границе:
1. получить внешние входные данные
2. проверить структуру
3. нормализовать форму данных
4. передать доверенное значение в доменную логику

---

## 4. Правила для функций

- Одна функция должна выполнять одну задачу.
- Сохраняй узкую и связную ответственность функций.
- Отделяй чистую логику от побочных эффектов.
- По возможности сокращай число параметров.
- Для больших списков аргументов предпочитай параметры в виде объекта, когда это улучшает ясность.
- Избегай булевых флагов, меняющих поведение.
- Не выстраивай цепочки `map`, `filter`, `sort` и подобных преобразований непосредственно на результате `await`, когда промежуточная переменная делает код понятнее.
- Предпочитай одну переменную для загруженных данных и вторую для результата преобразования, если преобразование имеет самостоятельный смысл.

### Предпочитай
```js
getPrice(product, { mode: 'discounted' })
```

### Избегай
```js
getPrice(product, true)
```

### Предпочитай
```js
const tickers = await client.getTickers()
const filteredTickers = tickers.filter(isLiquidTicker)
```

### Избегай
```js
const tickers = (await client.getTickers()).filter(isLiquidTicker)
```

Не изменяй входные аргументы без ясной и осознанной причины.

---

## 5. Правила именования

- Имена должны выражать назначение, а не неопределённую форму.
- Последовательно используй доменный язык.
- Предпочитай точные имена коротким.
- Не используй одну переменную для нескольких смыслов.

Избегай общих имён вроде:
- `data`
- `obj`
- `item`
- `tmp`
- `res`
- `processData`
- `handleStuff`

Если для объяснения имени нужен комментарий, переименуй его.

---

## 6. Правила потока управления

- Уменьшай вложенность.
- Используй защитные проверки и ранние возвраты.
- Выноси сложные условия в переменные с понятными именами, когда это улучшает читаемость.
- Не пиши условия, требующие мысленной расшифровки.

### Предпочитай
```js
function canProcessOrder(order) {
  if (!order) return false
  if (!order.items?.length) return false
  if (!order.isPaid) return false

  return true
}
```

---

## 7. Правила для объектов и массивов

- Не злоупотребляй цепочками преобразований, когда простой цикл понятнее.
- Используй `map`, `filter` и `reduce` только тогда, когда они улучшают читаемость.
- Не используй `reduce` как универсальный инструмент по умолчанию.
- Используй деструктуризацию, когда она уменьшает шум, а не скрывает контекст.
- Избегай скрытого изменения общих объектов или массивов.

Предпочитай простой перебор хитроумным цепочкам обработки, когда логика становится плотной.

---

## 8. Правила асинхронности и промисов

- Предпочитай `async/await`.
- Ожидай завершения операций, когда важен порядок.
- Используй `Promise.all` только для действительно независимой работы.
- Используй `Promise.allSettled`, когда допустим частичный сбой.
- Ограничивай параллельность при запуске множества асинхронных задач.
- Никогда не оставляй отклонения промисов необработанными.

Каждый промис должен:
- ожидаться через `await`
- возвращаться
- либо явно обрабатываться

Не запускай асинхронную работу «в фоне», если такое поведение не является намеренным и безопасным.

---

## 9. Правила обработки ошибок

- Не подавляй ошибки.
- Либо содержательно обработай ошибку, либо выброси её повторно.
- Добавляй контекст при логировании или передаче ошибок дальше.
- Сохраняй единую стратегию ошибок внутри слоя.
- Не используй исключения для обычного ожидаемого потока управления, если слой явно не придерживается такой политики.

### Избегай
```js
try {
  await saveUser(user)
} catch (error) {}
```

### Предпочитай
```js
try {
  await saveUser(user)
} catch (error) {
  logger.error('Failed to save user', { error, userId: user.id })
  throw error
}
```

---

## 10. Правила модулей и архитектуры

- Сохраняй связность ответственности модулей.
- Разделяй транспорт, валидацию, бизнес-логику, хранение и преобразования данных.
- Предпочитай небольшие модули с узкой ответственностью «божественным файлам».
- Не превращай `utils` в свалку.
- Делай границы явными.

По умолчанию избегай:
- огромных файлов со смешанной ответственностью
- необработанных объектов запроса/ответа глубоко внутри доменного кода
- необработанных данных внешних API в бизнес-логике
- абстракций, введённых до появления реальных вариаций

---

## 11. Правила для классов и `this`

- Не используй классы по привычке.
- Не опирайся на `this`, когда функция или обычный объект проще.
- Используй классы, когда они улучшают моделирование, инкапсуляцию состояния, управление жизненным циклом или инварианты.
- Избегай статических утилитарных классов, которые лишь имитируют пространства имён.

Выбирай структуру, которая делает поведение понятнее и безопаснее.

---

## 12. Правила состояния и изменений

- Минимизируй общее изменяемое состояние.
- Предпочитай локальные управляемые изменения глобальным неявным изменениям.
- Используй обновления с сохранением неизменяемости, когда они делают поведение безопаснее и понятнее.
- Не копируй объекты механически, если это лишь добавляет шум.

Цель — управляемые изменения состояния, а не формальная неизменяемость.

---

## 13. Правила равенства и приведения типов

- Предпочитай строгое равенство.
- Будь осторожен с проверками truthy/falsy.
- Не полагайся на неявное приведение типов там, где важно точное поведение.
- Явно проверяй `null` / `undefined` / пустую строку / ноль, когда эти случаи семантически различаются.

### Избегай
```js
if (!value) {
  // ...
}
```

когда `0`, `''`, `false`, `null` и `undefined` неэквивалентны в данном контексте.

---

## 14. Правила для комментариев

- Комментарии должны объяснять причины, а не повторять действия.
- Используй комментарии для ограничений, особенностей протокола, компромиссов и неочевидных решений.
- Не компенсируй комментариями неудачные имена или запутанный код.
- Пиши полезные TODO с контекстом.

Если коду нужно много поясняющих комментариев, сначала упрости код.

---

## 15. Правила логирования

- Логируй события и контекст, а не шум.
- Не логируй секреты или чувствительные данные.
- Логирование не заменяет правильную обработку ошибок.
- По возможности предпочитай структурированные логи.

Избегай логирования:
- паролей
- токенов
- полных платёжных данных
- ненужных персональных данных

---

## 16. Правила использования инструментов

Используй автоматизированные проверки.

Рекомендуемый базовый набор:
- ESLint
- форматтер
- тесты
- обязательные проверки в CI

Предпочитай правила, обнаруживающие реальные ошибки и рискованные паттерны, спорам только о стиле.

Полезные области автоматического контроля:
- случайные глобальные переменные
- необработанные промисы
- недостижимый код
- опасные паттерны равенства/приведения типов
- непоследовательные импорты
- сложность, превышающая стандарты команды

---

## 17. Правила тестирования

- Рассматривай тестируемость как показатель качества проектирования.
- Отделяй бизнес-логику от ввода-вывода, чтобы упростить тестирование.
- Тестируй доменные правила, инварианты, обработку ошибок и интеграции.
- Не пиши тесты только ради увеличения показателей покрытия.
- Избегай решений, требующих чрезмерного использования заглушек для простого поведения.

---

## 18. Правила безопасности и защитного программирования

- Никогда не доверяй внешним входным данным.
- Проверяй данные перед использованием в SQL, shell-командах, HTML, шаблонах, файловых путях или вызовах внешних сервисов.
- Различай валидацию и очистку данных.
- Считай строки извне системы потенциально небезопасными, пока не доказано обратное.

Валидация отвечает на вопрос:
- допустимы ли данные?

Очистка данных отвечает на вопрос:
- безопасны ли данные для этого конкретного контекста?

Не путай эти понятия.

---

## 19. Предпочтительная основа новых JavaScript-проектов

### Языковая основа
- `const` по умолчанию
- `let` только при необходимости
- без `var`
- `===` / `!==`
- `async/await`
- ранние возвраты
- содержательные имена

### Архитектурная основа
- валидация на границах
- отделение ввода-вывода от бизнес-логики
- узкая ответственность модулей
- минимум общего изменяемого состояния

### Инструментальная основа
- ESLint
- форматтер
- тесты
- CI

### Основа безопасности
- никогда не доверять внешним входным данным
- проверять данные окружения / HTTP / JSON / внешних API
- избегать логирования чувствительной информации

---

## 20. Приоритеты рефакторинга

При рефакторинге JavaScript-кода:
1. сохраняй поведение
2. улучшай имена
3. уменьшай скрытые побочные эффекты
4. уменьшай вложенность
5. упрощай поток управления
6. изолируй изменения состояния
7. изолируй ввод-вывод от бизнес-логики
8. удаляй ненужные абстракции

Не превращай при рефакторинге решение в более абстрактное, но менее читаемое.

---

## 21. Антипаттерны, которых следует избегать

- `var`
- широкие предположения на основе truthy/falsy
- молчаливый перехват ошибок
- огромные многоцелевые функции
- скрытые изменения общего состояния
- необработанные внешние данные глубоко в бизнес-логике
- булевы флаги режимов
- пирамиды обратных вызовов, когда `async/await` понятнее
- утилитарные модули без доменной структуры
- абстракции без реальной необходимости
- код, зависящий от хрупкого поведения `this`
- хитроумные однострочные выражения, ухудшающие читаемость

---

## 22. Стандарт результата

Сгенерированный JavaScript-код должен быть:
- корректным
- явным
- читаемым
- поддерживаемым
- предсказуемым
- согласованным со стилем репозитория

Если приходится выбирать между хитроумностью и поддерживаемостью, выбирай поддерживаемость.
