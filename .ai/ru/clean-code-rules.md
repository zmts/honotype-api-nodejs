# Правила чистого кода

## Назначение

Этот документ определяет базовые правила чистого кода, которыми необходимо руководствоваться при генерации, изменении, рефакторинге и ревью кода.

Цель — не максимальная абстракция и не стилистическое совершенство.
Цель — код, который:

- легко читать
- легко изменять
- трудно случайно сломать
- явно выражает намерение
- соразмерен задаче

При конфликте правил предпочитай меньшую сложность, более ясное намерение и более простую поддержку.

---

## Основной принцип

Код пишется прежде всего для людей.
Машины лишь выполняют его.

Читаемый, обычный и явный код обычно лучше хитроумного.

---

## 1. Предпочитай читаемость хитроумным решениям

Не сжимай код только потому, что это технически возможно.
Избегай хитроумных однострочных выражений, если они ухудшают ясность.

### Предпочитай
- явные имена
- простой поток управления
- очевидные преобразования данных
- промежуточные переменные, когда они улучшают понимание

### Избегай
- плотных цепочек выражений с неясным смыслом
- скрытых побочных эффектов внутри выражений
- чрезмерного использования сокращённого синтаксиса, скрывающего намерение

### Пример

Плохо:

```ts
const r = a.filter(x => x.s && x.t && x.u).map(x => ({ ...x, z: 1 }))
```

Лучше:

```ts
const eligibleUsers = users
  .filter(isEligibleUser)
  .map(markAsProcessed)
```

## 2. Одна функция должна выполнять одну задачу

У функции должна быть одна понятная ответственность.
Если она проверяет данные, сохраняет их, отправляет уведомления, форматирует результат и пишет логи — она делает слишком много.

### Признаки перегруженной функции
- в ней есть секции с несвязанными ответственностями
- она смешивает бизнес-логику с инфраструктурными задачами
- в ней много условных ветвей по несвязанным причинам
- её имя содержит `and`, `then` или несколько глаголов

### Предпочитай
- небольшие функции с узкой ответственностью
- координацию в одном месте, реализацию в меньших единицах
- отделение бизнес-логики от ввода-вывода

### Структура функции и порядок аргументов

Располагай логику в порядке выполнения: проверки и ранние выходы → подготовка значений → основная операция → результат. Разделяй смысловые этапы пустой строкой. Называй промежуточные значения по их роли; не создавай переменные и секции только ради оформления. Не повторяй вычисления и проходы по данным без необходимости.

Сначала передавай немногочисленные обязательные аргументы позиционно, затем — необязательные параметры одним объектом. Если обязательных и необязательных аргументов вместе много или их порядок трудно запомнить, используй один типизированный объект с обязательными и необязательными полями. Не группируй аргументы механически, если объект ухудшает ясность вызова.

```ts
function estimateRemainingMs(
  completed: number,
  total: number,
  options: { elapsedMs?: number; minimumMs?: number } = {},
): number | null {
  const elapsedMs = options.elapsedMs ?? 0;
  const hasInvalidInput = completed <= 0 || total < completed || elapsedMs < 0;
  if (hasInvalidInput) return null;

  const remaining = total - completed;
  const msPerItem = elapsedMs / completed;
  const estimatedMs = Math.ceil(remaining * msPerItem);

  return Math.max(estimatedMs, options.minimumMs ?? 0);
}
```

## 3. Используй имена, объясняющие намерение

Имена должны раскрывать назначение, а не только детали реализации.
Хорошее имя уменьшает потребность в комментариях.

### Предпочитай
- `activeUsers`
- `canProcessOrder`
- `withdrawalLimit`
- `isExpired`

### Избегай
- `data`
- `arr`
- `tmp`
- `value2`
- однобуквенных имён за пределами небольших локальных циклов

### Правило
Если для объяснения смысла имени нужен комментарий, имя, вероятно, неудачное.

---

## 4. Уменьшай вложенность

Глубокая вложенность увеличивает когнитивную нагрузку.
Используй защитные проверки и ранние возвраты, чтобы сделать поток управления более плоским.

### Предпочитай

```ts
function canProcessOrder(order: Order | null): boolean {
  if (!order) return false
  if (!order.items.length) return false
  if (!order.isPaid) return false

  return true
}
```

### Избегай

```ts
function processOrder(order) {
  if (order) {
    if (order.items?.length) {
      if (order.isPaid) {
        return true
      }
    }
  }

  return false
}
```

## 5. Не дублируй логику без причины

Дублирование приводит к расхождениям.
Когда одна копия меняется, а другая нет, появляются ошибки.

### Предпочитай
- выделение действительно повторяющихся бизнес-правил
- централизацию общей логики валидации и преобразований
- последовательное переиспользование доменных понятий

### Избегай
- преждевременной абстракции после единственного использования
- универсальных вспомогательных функций, скрывающих доменный смысл

### Правило принятия решения
Небольшое дублирование часто лучше неправильной абстракции.
Выделяй общую логику только тогда, когда повторение действительно существует и устойчиво.

---

## 6. Делай бизнес-смысл видимым в коде

Код должен отражать доменное намерение, а не только механику.

### Предпочитай

```ts
if (user.canWithdraw(amount)) {
  // ...
}
```

Или:

```ts
const isWithdrawalAllowed =
  user.balance >= amount && user.status === UserStatus.ACTIVE
```

### Избегай

```ts
if (user.balance > amount && user.status === 1) {
  // ...
}
```

Доменный язык упрощает ревью кода и делает изменения безопаснее.

---

## 7. Делай модули небольшими и связными по ответственности

Большие файлы и «божественные объекты» — признак структурной проблемы.

### Предпочитай ясное разделение ответственности
- контроллер или обработчик: граница входных данных
- сервис или сценарий использования: бизнес-логика
- репозиторий: доступ к хранилищу
- преобразователь: преобразования между слоями
- утилита: общие функции без состояния, только когда они действительно универсальны

### Избегай
- огромных классов сервисов, выполняющих всё
- файлов, смешивающих транспорт, домен, хранение, форматирование и валидацию
- общих вспомогательных функций, превращающихся в свалку

---

## 8. Минимизируй скрытые зависимости

Единица кода должна максимально опираться на явные входные данные, а не на невидимое внешнее состояние.

### Предпочитай

```ts
function calculatePrice(cartTotal: number, taxRate: number): number {
  return cartTotal * taxRate
}
```

### Избегай

```ts
function calculatePrice(): number {
  return globalConfig.tax * currentCart.total
}
```

Явные зависимости улучшают тестируемость и предсказуемость.

---

## 9. Обрабатывай ошибки явно

Не подавляй ошибки.
Перехваченную ошибку нужно обрабатывать осознанно.

### Предпочитай
- добавление контекста
- логирование, когда оно уместно
- преобразование инфраструктурных ошибок в доменные ошибки или ошибки API
- повторное выбрасывание, если восстановление невозможно

### Избегай

```ts
try {
  await saveUser(data)
} catch (error) {}
```

### Лучше

```ts
try {
  await saveUser(data)
} catch (error) {
  logger.error('Failed to save user', { error, data })
  throw error
}
```

## 10. Комментарии должны объяснять причины, а не повторять действия

Хороший код обычно должен сам объяснять, что он делает.
Комментарии оправданны, когда сохраняют контекст, который код не может ясно выразить.

### Полезные комментарии
- неочевидные бизнес-ограничения
- особенности протокола
- обоснование обходного решения
- компромиссы производительности
- предположения о безопасности

### Слабые комментарии
- повторение кода
- описание тривиальных шагов
- компенсация неудачных имён

### Пример

Слабый:

```ts
// increment index
index++
```

Полезный:

```ts
// Inclusive end date is required because the upstream billing API treats the range end as part of the chargeable window.
```

---

## 11. Единообразие важнее личного стиля

Единообразную кодовую базу проще поддерживать, чем локально совершенную, но в целом непоследовательную.

### Следуй существующим соглашениям проекта в вопросах
- именования
- форматирования
- обработки ошибок
- асинхронных паттернов
- структуры файлов
- стиля тестирования
- порядка импортов
- именования DTO и типов

Не вводи новый стиль без ясной технической причины.

---

## 12. Избегай избыточного усложнения

Не создавай решение для гипотетической будущей сложности, если текущая задача проста.

### Избегай
- ненужных слоёв абстракции
- фабрик для простых конструкторов
- универсальных фреймворков вокруг тривиального CRUD
- избыточных промежуточных обращений
- архитектуры под несуществующий масштаб

### Предпочитай
- самую простую структуру, удовлетворяющую текущим требованиям
- точки расширения только там, где изменения вероятны
- прямолинейный код вместо поклонения паттернам

---

## 13. Тестируемость — показатель качества проектирования

Если код трудно тестировать, его структура часто слишком связана или слишком неявна.

### Предпочитай
- чистые функции, где это практично
- явные зависимости
- изолированные бизнес-правила
- детерминированное поведение

### Тревожные признаки
- сильная зависимость от глобальных значений
- скрытые источники времени или случайности
- побочные эффекты, смешанные с вычислениями
- сложная подготовка для простых тестов

Тестируемость — не единственная цель, но плохая тестируемость обычно указывает на проблемы проектирования.

---

## 14. Аккуратно разделяй данные, поведение и побочные эффекты

Не смешивай всё в анонимных объектах и утилитарных функциях.

### Предпочитай
- типизированные доменные модели
- поведение рядом с соответствующими доменными понятиями
- побочные эффекты, изолированные рядом с границами

### Избегай
- `any` для важных бизнес-объектов
- больших изменяемых структур, передаваемых повсюду
- доменных правил, разбросанных по несвязанным вспомогательным функциям

---

## 15. Активно удаляй код, который больше не помогает

Чистый код — это не только написание нового кода.
Это также удаление кода, который не приносит пользы.

### Удаляй, когда это безопасно
- мёртвый код
- устаревшие ветви
- неактуальные флаги функциональности
- неиспользуемые абстракции
- обходные решения для совместимости, которые больше не нужны
- дублирующие устаревшие пути выполнения

Каждая лишняя строка увеличивает стоимость поддержки.

---

## Практические правила принятия решений

При генерации или изменении кода применяй следующие приоритеты по порядку:

1. Сохраняй корректность.
2. Предпочитай ясность краткости.
3. Сохраняй соразмерность решения задаче.
4. Не вводи абстракции без ясной пользы.
5. Делай бизнес-намерение видимым.
6. Избегай скрытых побочных эффектов.
7. Следуй существующему стилю проекта, если он явно не вредит.

---

## Проверочный список для рефакторинга

Перед завершением работы над кодом проверь:

- Точны ли имена и выражают ли они смысл?
- Есть ли у каждой функции одна понятная ответственность?
- Можно ли уменьшить вложенность?
- Выделена ли повторяющаяся логика только там, где это уместно?
- Обрабатываются ли ошибки осознанно?
- Явны ли зависимости?
- Отражает ли код доменный смысл?
- Есть ли ненужные абстракции?
- Можно ли удалить какой-либо код?
- Сможет ли другой разработчик быстро это понять?

## Правила выбора компромиссов

Эти правила не абсолютны.
При конфликте правил руководствуйся здравым смыслом.

### Предпочитай немного более длинный код, когда
- его проще читать
- он явно показывает граничные случаи
- он уменьшает неоднозначность

### Предпочитай небольшое дублирование, когда
- абстракция вводила бы в заблуждение
- повторяющаяся логика может развиваться по-разному
- общая вспомогательная функция стала бы слишком универсальной

### Предпочитай простой процедурный код, когда
- задача линейна и невелика
- дополнительные паттерны добавили бы промежуточные обращения без пользы

### Предпочитай абстракцию, когда
- понятие устойчиво
- дублирование действительно существует и повторяется
- абстракция улучшает ясность, а не скрывает её

---

## Чего следует избегать по умолчанию

- хитроумных однострочных выражений, ухудшающих читаемость
- универсальных имён вспомогательных функций вроде `processData`, `handleResponse`, `doStuff`
- больших многоцелевых функций
- комментариев, повторяющих очевидный код
- молчаливого перехвата ошибок
- скрытого глобального состояния
- чрезмерного использования наследования
- введения паттернов без необходимости
- превращения понятного кода в абстрактный, но менее читаемый

---

## Ожидаемый результат

Итоговый код должен быть:

- понятным
- устойчивым
- поддерживаемым
- явным
- согласованным с проектом

Если приходится выбирать между впечатляющим и понятным кодом, выбирай понятный.
