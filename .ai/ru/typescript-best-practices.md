# Рекомендуемые практики TypeScript

## Назначение

Используй эти правила при генерации, изменении, рефакторинге и ревью TypeScript-кода.

Основная цель — корректный, читаемый, поддерживаемый код, соразмерный задаче.

При конфликте правил предпочитай:
1. корректность
2. ясность
3. явное доменное намерение
4. меньшую сложность
5. согласованность с существующей кодовой базой

---

## 1. Общие правила

- Предпочитай читаемый код хитроумному.
- Предпочитай явный код сжатому.
- Предпочитай устойчивые обычные решения впечатляющим абстракциям.
- Сохраняй соразмерность изменений задаче.
- Следуй существующим соглашениям проекта, если они явно не вредят.

Не вводи сложность без конкретной пользы.

---

## 2. Базовые правила безопасности типов

- По умолчанию используй настройки TypeScript с `strict`.
- Не используй `any` для обхода ошибок типизации. Для данных неизвестной структуры используй `unknown`, затем проверяй их или сужай тип перед использованием.
- Если `any` необходим из-за ограничения сторонней библиотеки или динамического интерфейса, локализуй его в минимальном участке интеграции, кратко объясни причину и не распространяй небезопасный тип в бизнес-логику.
- Считай внешние данные небезопасными до валидации.
- Используй `never` для исчерпывающих проверок дискриминируемых объединений.
- Не заменяй `any` необоснованным приведением типа: приведение не проверяет данные во время выполнения. Избегай небезопасных приведений через `as`, если есть лучший вариант.

### Подход по умолчанию
- внешние входные данные -> `unknown`
- проверенные входные данные -> типизированное доменное значение
- внутренний доменный код -> избегать `any`

---

## 3. Правила моделирования

- Предпочитай объединения строковых литералов неограниченному `string`.
- Предпочитай дискриминируемые объединения булевым флагам и свободным наборам необязательных полей.
- Представляй невозможные состояния как невозможные на уровне типов.
- Разделяй DTO, доменные модели и модели хранения.
- Используй вспомогательные типы только тогда, когда они улучшают ясность.

### Предпочитай
```ts
type Result =
  | { kind: 'success'; data: User }
  | { kind: 'error'; error: string }
```

### Избегай
```ts
type Result = {
  isSuccess: boolean
  data?: User
  error?: string
}
```

---

## 4. Правила валидации во время выполнения

TypeScript не заменяет валидацию во время выполнения.

Всегда выполняй валидацию на границах, когда данные поступают из:
- HTTP-запросов
- очередей
- вебхуков
- переменных окружения
- JSON.parse
- локального хранилища
- внешних API
- файлов
- сторонних SDK

Предпочтительный порядок обработки на границе:
1. получить `unknown`
2. проверить с помощью схемы или защитной проверки
3. преобразовать в доверенное типизированное значение
4. использовать доверенное значение внутри системы

Не передавай необработанные внешние данные глубоко в доменную логику.

---

## 5. Правила для функций

- Одна функция должна выполнять одну задачу.
- Предпочитай небольшие функции с узкой ответственностью.
- Отделяй чистую логику от побочных эффектов.
- По возможности сокращай число параметров.
- Для больших списков аргументов предпочитай параметры в виде объекта, сохраняя их типизированными и содержательными.
- Избегай булевых флагов, меняющих поведение функции.
- Не выстраивай цепочки `map`, `filter`, `sort` и подобных преобразований непосредственно на результате `await`, когда промежуточная переменная сделала бы код понятнее.
- Предпочитай отдельную переменную для загруженных данных и другую для результата преобразования, если операция нетривиальна.

### Предпочитай
```ts
getPrice(product, { mode: 'discounted' })
```

### Избегай
```ts
getPrice(product, true)
```

### Предпочитай
```ts
const tickers = await client.getTickers()
const filteredTickers = tickers.filter(isLiquidTicker)
```

### Избегай
```ts
const tickers = (await client.getTickers()).filter(isLiquidTicker)
```

---

## 6. Правила именования

- Имена должны выражать намерение, а не неопределённую форму.
- Последовательно используй доменный язык.
- Предпочитай точные имена коротким.
- Избегай общих имён вроде:
  - `data`
  - `obj`
  - `item2`
  - `processData`
  - `handleStuff`

Если для объяснения имени нужен комментарий, переименуй его.

---

## 7. Правила сужения типов

- Естественным образом используй сужение типов на основе потока управления.
- Предпочитай `typeof`, `instanceof`, `in`, проверки дискриминанта и защитные проверки с ранним выходом.
- Выноси повторяющиеся проверки в пользовательские функции проверки типов, когда это полезно.
- Не создавай фиктивные функции проверки типов, которые на самом деле не доказывают заявленный тип.

### Предпочитай
```ts
function isUser(value: unknown): value is User {
  return typeof value === 'object' && value !== null && 'id' in value
}
```

---

## 8. Правила обработки ошибок

- Не подавляй ошибки.
- В `catch` рассматривай ошибку как `unknown` до сужения типа.
- Добавляй контекст при повторном выбрасывании или преобразовании ошибок.
- Сохраняй единую стратегию ошибок внутри слоя.

Возможная стратегия по слоям:
- домен -> объединения `Result` или явные доменные ошибки
- прикладной слой/сервисы -> преобразованные ошибки
- HTTP-слой -> преобразование ответа с учётом транспорта

Избегай молчаливого перехвата ошибок.

---

## 9. Правила модулей и архитектуры

- Сохраняй связность ответственности модулей.
- Делай границы явными.
- Разделяй транспорт, домен, хранение, валидацию и преобразования данных.
- Предпочитай простые модули «божественным файлам».
- Не вводи интерфейсы или абстракции до появления реальных вариаций.

### По умолчанию избегай
- универсальных слоёв manager/factory/resolver без реальной необходимости
- интерфейсов репозиториев с единственной тривиальной реализацией без вариаций
- глубоко вложенных промежуточных обращений вокруг простого CRUD

---

## 10. Правила для классов и объектов

- Не используй классы по привычке.
- Используй классы, когда они улучшают моделирование, инварианты, управление жизненным циклом или инкапсуляцию.
- Предпочитай функции и обычные объекты, когда они проще и понятнее.
- Не превращай всё принудительно в ООП или процедурный стиль.

Выбирай структуру, которая делает предметную область понятнее.

---

## 11. Правила неизменяемости

- Используй `const` по умолчанию.
- Предпочитай `readonly` и `ReadonlyArray` на границах, где изменения должны быть запрещены.
- Избегай неконтролируемого изменения общего состояния.
- Не добавляй формальную неизменяемость, не отражающую реальное поведение.

---

## 12. Правила линтинга и инструментов

Используй автоматизированные проверки.

Рекомендуемый базовый набор:
- `tsc --noEmit`
- ESLint
- `typescript-eslint`
- форматтер
- тесты
- обязательные проверки в CI

Предпочитай правила линтера, обнаруживающие семантические проблемы, спорам только о стиле.

В первую очередь выявляй:
- небезопасный `any`
- небезопасный доступ к членам
- необработанные промисы
- непоследовательные импорты
- ненужные приведения типов

---

## 13. Правила тестирования

- Рассматривай тестируемость как показатель качества проектирования.
- Отделяй бизнес-логику от ввода-вывода, чтобы упростить тестирование.
- Тестируй доменные правила, инварианты, преобразования и поведение контрактов.
- Не пиши тесты только ради формальных показателей количества протестированных функций.
- Избегай решений, требующих подмены половины системы для простого теста.

---

## 14. Правила для комментариев

- Комментарии должны объяснять причины, а не повторять действия.
- Используй комментарии для ограничений, особенностей протокола, компромиссов, обходных решений и неочевидных решений.
- Не компенсируй комментариями неудачные имена или чрезмерно сложный код.

Если коду нужно много поясняющих комментариев, сначала упрости код.

---

## 15. Предпочтительная основа новых TypeScript-проектов

### Базовый tsconfig
```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "useUnknownInCatchVariables": true,
    "noImplicitOverride": true
  }
}
```

### Основа обработки данных
- внешние данные = `unknown`
- валидация на входе
- преобразование в доверенные типы
- использование доверенных типов внутри доменной логики

### Основа моделирования
- объединения вместо магических строк
- дискриминируемые объединения вместо свободных наборов необязательных полей
- исчерпывающие проверки доменных состояний

---

## 16. Приоритеты рефакторинга

При рефакторинге TypeScript-кода:
1. сохраняй поведение
2. улучшай имена
3. уменьшай небезопасную типизацию
4. уменьшай дублирование там, где оно устойчиво
5. уменьшай вложенность
6. изолируй побочные эффекты
7. сохраняй соответствие типов доменному смыслу
8. удаляй ненужные абстракции

Не превращай при рефакторинге решение в более абстрактное, но менее читаемое.

---

## 17. Антипаттерны, которых следует избегать

- широкое использование `any`
- небезопасные цепочки `as`
- свободные объекты с множеством необязательных полей, моделирующие несколько состояний
- булевы флаги режимов
- огромные многоцелевые функции
- транспортные DTO, переиспользуемые как доменные сущности
- необработанные внешние данные, поступающие в бизнес-логику
- молчаливый перехват ошибок
- имена вспомогательных функций без доменного смысла
- слои абстракции без реальных вариаций
- чрезмерно хитроумные обобщённые типы, ухудшающие читаемость

---

## 18. Стандарт результата

Сгенерированный TypeScript-код должен быть:
- типобезопасным
- явным
- читаемым
- ориентированным на предметную область
- простым для изменения
- согласованным со стилем репозитория

Если приходится выбирать между хитроумностью и поддерживаемостью, выбирай поддерживаемость.
